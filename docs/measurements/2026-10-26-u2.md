# U2 — kernel memory a module gets in process context (2026-10-26)

- **Measurement:** U2 (90 §3, 30 §8): how much kmem a module's `_load`
  gets in total, in process context after multi-user (`modadmin -l`
  under development load). The probe takes 64 KiB `KM_NOSLEEP` pieces
  until one fails, then gives them all back.
- **Class:** bench (amiberry), plan item S3-41.
- **Tool:** the probe module `u2kva` (`tests/bench/s3-41`), built with the
  kit, 64 KiB pieces (k46 `fc7d439c…`, k30 `34c32892…`). It ran on the
  kernels of record, in a generation with the arena, with `modadmin -K`
  first, in a boot without U4.
- **Evidence:** the Bench's runs N81 (k46, 128 MB in the CPU board's bank)
  and N82 (k30, 64 MB, the line's maximum).

## 1. Results

| | k46 N81 (128 MB) | k30 N82 (64 MB) |
|---|---|---|
| probe line | `u2kva: 5 chunks of 65536 bytes (320 KiB) with KM_NOSLEEP, from 0x403E4000 to 0x40434000` | `u2kva: 10 chunks of 65536 bytes (640 KiB) with KM_NOSLEEP, from 0x40396800 to 0x40436800` |
| given back | `all 5 given back` | `all 10 given back` |
| load, unload, halt | rc 0, rc 0, clean | rc 0, rc 0, clean |

The pieces are 64 KiB, so the total lies between 320 and 383 KiB on k46,
and between 640 and 703 KiB on k30. The first run (N79/N80, 256 KiB
pieces, while U4's stuck request held memory) is void.

k46 at 128 MB gets half of what k30 gets at 64 MB, matching U4's
largest single request (256 KiB on k46, 512 KiB on k30). The kernel map
these requests come from is shared with `page[]`, which grows with RAM.

## 2. What it means

- **The core's working set for a load from a file.** The core holds all
  of it at once, as `KM_SLEEP` requests:
  - the file buffer for the SHA-256 check (the file size rounded up to a
    power of two, at least 8 KiB);
  - the section, symbol and string tables;
  - the image;
  - the module's symbol table.

  Computed from the objects (upper bounds):

  | Module | file | buffer | image | tables | module table | total |
  |---|---|---|---|---|---|---|
  | monsw | 5 197 | 8 192 | 2 215 | 2 745 | 1 833 | about 15 KB |
  | z3660eth | 18 787 | 32 768 | 12 880 | 6 719 | 5 071 | about 57 KB |
  | z3660rtg | 30 765 | 32 768 | 20 859 | 7 821 | 5 941 | about 67 KB |
  | cdfs (its kernel object) | 97 611 | 131 072 | 69 095 | 17 799 | 14 063 | about 232 KB |
  | at C3-1's limit | under 262 144 | 262 144 | 262 159 | | | over 524 288 |

- **On k46 a module at C3-1's 256 KiB limit cannot load in process
  context**: its buffer and image alone exceed the total. Because the
  core's requests are `KM_SLEEP`, such a load does not fail: it waits,
  as U4's `KM_SLEEP` request did, possibly forever. The image and file limit (C3-1 §6) is a ceiling, not a
  budget.
- **Today's modules fit.** z3660eth and z3660rtg need under a quarter of
  k46's total. A cdfs-sized module would take about 72 % of it.
- **Larger modules load before multi-user or from the arena.** Boot class
  loads at the first `sysinit` entry; root class (stage 4) loads from the
  arena, where the loader has placed the image and the core takes no kmem
  for the file or the image. The totals at those points are not
  measured. U1 found single `KM_NOSLEEP` requests of 1 MiB (k30) and
  2 MiB (k46) succeed at `dmainit` and at the hook.
- **Spec 30 §8** carries the rule that follows.
