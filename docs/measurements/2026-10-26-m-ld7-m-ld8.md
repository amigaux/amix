# M-LD7 and M-LD8 — checksum and inflate time on a 25 MHz 68030 (2026-10-26)

- **Measurements:** M-LD7 (CRC-32 and SHA-256 time over a kernel; decides whether the loader checks SHA-256), M-LD8 decode-time part (the ratio part is in `2026-10-25-m-net1.md`)
- **Class:** bench, upper bound. A cycle-exact 68030 with a 68882 at 25 MHz (instruction cache with burst, data cache, 2 MB chip and 80 MB fast memory, Kickstart 47.115) on the project's emulator. A 68060 model ran too, but at emulator speed (host-bound), so its figures are not 68060 figures. Metal: S1-26.
- **Tool:** `tools/measure/axtime.c` (an AmigaDOS program running the loader's own C, timed with the E-clock under Forbid); inputs from `tools/measure/m-ld7.sh`
- **Raw output:** the workspace's `tmp/2026-10-26-s1-measure/m-ld7/` (m030/axtime.txt, m060/axtime.txt, cpu.txt)

## 3. M-LD7: the loader checks CRC-32 only

SHA-256 would add 2.3 s (k30) to 3.75 s (k46) to every boot on a 25 MHz
68030, 6.3 times the CRC-32 it would sit beside. The loader's CRC-32 covers
medium damage, which is its job (`60-signing-and-publishing.md` §3). The
SHA-256 checks belong elsewhere: apkg after download, `kbootset check`
over the store, and the kernel for every module against the booted
manifest. **Verdict: the loader does not check SHA-256** (10 §5.1). The
68060 metal figure (S1-26) is for the record only.

## 4. M-LD8: why the first decoder was slow, and the second

The first decoder took 26.96 s to inflate 1 267 045 bytes, about 530
cycles per output byte, against 7 for a copy. It ran from fast memory with
both caches on, so the cost is the decoder itself, not where it ran. It
decoded each Huffman code one bit at a time: a call to `bits()` per bit, a
variable shift and mask, and the canonical-code loop. A literal took about
290 68030 instructions.

**Second decoder** (this commit, `loader/common/inflate.c`):
- a 512-entry table indexed by the next 9 input bits gives the symbol and
  code length of every code of up to 9 bits in one lookup; longer codes,
  which are rare, still go bit by bit;
- the main loop keeps the bit buffer and both positions in registers;
- matches are copied through pointers.

A literal is now about 35 68030 instructions (counted in the gcc-cross-amix
output). On the host it is 3.0 times faster: k30.z inflates in 5.6 ms
instead of 16.7 ms, k46.z in 7.7 ms instead of 24.3 ms. On the 68030,
where calls and memory traffic cost more, the estimate is **6–10 times**:
about 3–4.5 s for k30 and 4–6 s for k46. axtime re-runs it.

The checks it passes:
- 3 000 zlib streams (random, text-like, run-length and repetitive data
  up to 64 KiB, every level and strategy including fixed codes and Huffman
  only) inflate identically;
- so do both 1.0 floppy kernels (`tests/host/inflate-kernels.sh`) and the
  518 host checks.

boot2 grows to 27 528 bytes (image + bss 27 920 of 28 672). The tables
(about 2 KB more state) live in boot2's allocated work area, not in bss.

**Chip memory: the second lever.** boot1 loads boot2 into chip memory
(the strap's device reads by DMA), so boot2's code runs from chip RAM, but
its tables and the kernel buffer are in fast RAM. `axtime-chip` is the
same program with its code loaded into chip memory (`b2link -h -c`) and
its tables allocated in fast memory: that is boot2's arrangement exactly.
The run of both builds shows what moving boot2 into fast RAM at start-up
would gain. That move would be a few instructions in `start.s`, and it is
not made until the figure says it is worth it.

## 5. Judgement (spec change after freeze, 10 §5.5, 40 §3.2)

**Raw where there is room; deflate only where a generation must fit.**
- On a disk store (64 MiB) and on the CD, a kernel is stored raw. Reading
  an extra 0.7–1.3 MB from a hard disk or a CD costs well under a second.
  Inflating costs seconds on a 68030, even with the second decoder.
- The floppy pair and the netinstall medium store members deflated,
  because they must fit (M-FP1). There, a floppy reads about 27 KiB/s and
  deflate saves more reading time than the second decoder spends.

**Still open: the reference.** 10 §5.5 keeps LZW only if deflate loses on
ratio or on decode time. The ratio is won (73 % and 71 % of the LZW size,
M-LD8). The decode time against the stock LZW loader is measured on the
same model:
1. Boot the 1.0 boot floppy (`amix-installng/floppies/build/amix_21_boot-universal-r7.adf`:
   the stock bootblock and loader, K030-U-FD as an LZW stream of
   732 193 B) from DF0 on the 25 MHz 68030 model, from cold.
2. Then boot our one-volume floppy with the same kernel family
   (`ld-fd-030.adf` from S1-19: our loader, K030-U-FD deflated to
   534 142 B) on the same model, with the second decoder.
3. Time both from reset to the kernel's banner, with a boot frame every
   second.

The floppy reads differ (deflate reads about 200 KB less), so compare the
totals: that is what a user waits for. Our loader prints when it starts
and when it hands over; the stock loader shows the same span on its
frames.
