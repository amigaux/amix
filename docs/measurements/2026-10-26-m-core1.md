# M-CORE1 — the adopted core's host tests on our toolchains (2026-10-26)

- **Measurement:** M-CORE1 (90 §3, U13): the adopted core's host tests,
  built with our toolchain. Stage-3 plan item S3-01.
- **Class:** bench (host).
- **Tool:** `tests/core/run.sh` (`make core`).
- **Inputs:**
  - the core: `core/upstream/` (kdedon's DLM core, MIT, at
    `b736c59dc79d20b8b007a182a9b03c7b8efa461a`, unmodified) with
    `core/series` applied to a staged copy;
  - the kernels of record, read-only from amix-kerntools: KD060-Z (k46,
    `ET_REL` as shipped) and K030-U's `.etrel` (k30, before `elf2brel`).
    Each is bound at 0x08000000 with `m68k-elf-ld`, as boot2 binds the
    kernel on the Z3660 rows: the shipped form leaves `etext`, `edata`
    and `end` to the loader, and the tests need a bound image, as
    upstream's did;
  - gcc-cross-amix (the pin, GCC 2.7.2.3, `AMIX_KERNEL_CFLAGS`) for the
    kernel objects and modules;
  - GCC 14's binutils (`m68k-elf-ld`, `-nm`, `-readelf`) for the
    oracle's link;
  - the host's `cc` (GCC 15.2) for the host tools.
- **Raw output:** this repository's `build/core-run.log`, untracked.

## 1. What runs

The runner does what upstream's `build.sh` and `test/run.sh` do, calling
upstream's tools and helper scripts unmodified. The one omission is the
two A/UX objects: they need upstream's `coff2elf` and an A/UX tree, and
have no counterpart here.

1. **Host tools:** `mkksym`, `modfix`, the host build of the loader
   (`reloc`), and the core against simulated kernel services (`state`).
2. **Kernel objects:** `dlm.o` with gcc-cross-amix, with no warning
   beyond the stock headers' own.
3. **User side:** `libmod.a` and `modadmin`.
4. **Per kernel:**
   - the symbol block;
   - four modules built by `mkmod`: `dlmdep`, `dlmtest`, `dlmtest2`
     (`-O2 -m68040`) and `rall` (every relocation type);
   - the relocation oracle: each module relocated by the host loader must
     be byte-identical to `m68k-elf-ld` linking it at the same base;
   - the error paths;
   - the state harness.

## 3. Finding: the trampolines' hold across `longjmp` (patch 0001)

On the first run the state harness failed three checks on both kernels,
all in the exec trampoline's `longjmp` path: "drops the hold", "idle
module unloads", "load failure falls through". At `-O0` all 105 passed.

**The cause:**
- `xcall()` and `dlm_cdev_open()` set the hold (`h.m`) after
  `DLM_SETJMP`, and read it on the `longjmp` path to drop the hold.
- ISO C leaves a non-volatile automatic modified after `setjmp`
  indeterminate after the `longjmp`. Upstream kept `h` in memory by
  making it a one-member struct.
- GCC 15 at `-O` splits such a struct into a register, so the path read
  a stale 0, the hold leaked, and the next two checks followed from it.
- GCC 2.7.2.3's code for `xcall()` keeps `h.m` in the frame
  (`tst.l -76(%fp)` after the `longjmp`), so today's kernel build was
  right. The code was right by accident of the compiler, not by the
  language.

**The fix:** `core/patches/0001-trampoline-hold-volatile.patch` declares
`h` `volatile` at both sites. After it, the harness passes 105 of 105 on
both kernels, and `dlm.o`'s text is the same 25 812 bytes, so the kernel
code does not grow. The patch is listed in `core/README.md` as one to
offer upstream (OQ-30.6).

## 4. Verdict

**M-CORE1 holds on both lines.** The adopted core builds with our pinned
kernel compiler without warnings of its own. Its loader relocates every
type byte-identically to the cross linker and refuses every malformed
object with the right errno. Its state machine passes upstream's whole
harness. One portability fix entered the queue as patch 0001.
