# ramdisk — the RAM disk

`ramdisk` is a block driver on major 20 with three units:

| Unit | Node | What it is |
|---|---|---|
| 0 | `/dev/dsk/ram0` (`b 20 0`) | the miniroot image the boot loader placed in memory, when there is one |
| 1 | `/dev/dsk/ram1` (`b 20 1`) | a scratch disk of `size1` KiB, default 512 |
| 2 | `/dev/dsk/ram2` (`b 20 2`) | a scratch disk of `size2` KiB, default 2048 |

A medium that roots on a RAM disk (a CD, a floppy, a network install) carries this module, and
the kernel mounts its root from unit 0. An installed disk may carry it for the scratch units
alone.

It is a loadable kernel module of class `root` for both Amix kernel lines, `k30` (68030) and
`k46` (68040/68060), built with amix-dlm's ABI kit. The contracts it implements are amix-dlm's
C4-2 (a root-class driver, §8's ramdisk row) and C4-3 (the RAM-disk hand-off, §4).

Stock Amix 2.1 has a RAM disk on the same major: the `ram` driver, with three kmem-backed units
of 128 KiB, 512 KiB and 2 MiB, each allocated in one piece at its first open. It cannot present
an image that was loaded before the kernel started. The module kernels leave `ram` out of the
block switch, and this module takes the row. It keeps minors 1 and 2 as scratch disks of the
stock sizes. There is no static form of this driver: the stock `ram` is the static driver it
replaces.

## The units

**Unit 0, the image.** At load, the module asks the kernel for the image with
`ramdisk_image(&paddr, &size)`, a DDI name of kabi minor 2 (k30.1.2, k46.1.2):
- If it returns `ENOENT`, there is no image. Unit 0 does not exist: its open gives `ENXIO` and
  its size is -1.
- If it returns 0, unit 0 is `size` bytes at physical address `paddr`, rounded down to whole
  512-byte blocks. The console says `ramdisk: unit 0 is the image at 0x…, N KiB`.

The memory under the image belongs to the loader. boot2 places it at the top of the largest
fast-memory region, and shortens that region in the kernel's memory list, so the kernel never
puts those pages on a free list (C4-3 §2–§3). The module never allocates or frees it. The unit
is writable: the miniroot needs a writable `/tmp`. Its contents are lost at power-off.

**How unit 0 is reached.** boot2 places the image below `VSECT1` (0x40000000). The kernel maps
physical addresses below `VSECT1` one to one on both lines, so the image's kernel address is
`phystokv(paddr)`, which is the identity. No page table is built and nothing is mapped:
there is no `sptalloc`, `dev_kvmap` or `vtop` on this side, and nothing to undo. So there is
nothing to defer to a first open either. (The first open of unit 0 is the root mount, which
runs in the same root pass as `_load` anyway.) If an image ever lay at or across `VSECT1`,
the module would say `ramdisk: the image at 0x…, 0x… bytes, is not below 0x40000000; no
unit 0` and go on with units 1 and 2. It does not map such an image: `sptalloc`'s 4 MiB map
could not hold a miniroot.

**Units 1 and 2, the scratch disks.** Their memory is allocated at the first open and freed at
the last close, as the stock `ram` does it:
- It comes in pieces of at most 256 KiB, each one `kmem_zalloc(n, KM_NOSLEEP)`. C3-6 §1.1 allows
  no larger request: a running k46 box gives no more than 256 KiB in one piece. A 2 MiB unit is
  8 requests; the largest unit, 16 MiB, is 64.
- The memory is zero-filled, so a fresh scratch disk reads as zeros.
- If a request fails, the pieces already allocated are freed and the open gives `ENOMEM`. On a
  box whose kernel heap is busy that can happen; the open can simply be retried later.
- The module counts the open types (block, mount, swap) separately. The memory is freed only
  when the last one closes.
- A unit whose size parameter is 0 does not exist: `ENXIO`, size -1.

**Transfers.** Every transfer is a copy by the CPU (`bcopy`). There is no DMA.
- A transfer within the unit copies what fits and leaves the rest in `b_resid`.
- A read that starts exactly at the end transfers nothing, without an error.
- A write that starts at the end, a transfer that starts past it, a negative block, or a
  scratch unit that is not open, gives `ENXIO` with `B_ERROR`.
- The buffer is reached as the stock `ram` driver reached it: `vtop()` of the buffer's
  address, page by page, at `phystokv()` of the result. Each copy stays within one buffer
  page and within one kmem piece.
- Every request ends with `iodone(bp)`.

**The block switch row** holds open, close, strategy, print and size:
- `d_size` reports the unit's size in 512-byte blocks: the image's size for unit 0, the
  parameter's size for units 1 and 2 (whether open or not). It reports -1 for a unit that
  does not exist.
- `d_print` prints `ramdisk N: <message>`.
- There is no character row: no raw device, as in the stock driver.
- Opens of the character and layered types give `ENODEV`.

## The module

| `.moddata` key | Value |
|---|---|
| `name` | `ramdisk` |
| `class` | `root`: boot2 places it and the core links it before the root is mounted (C4-2) |
| `match` | `always` |
| `majors` | `b:20` (registered to `ramdisk` in the kit's `registry/majors`) |
| `unload` | `never`: a block row needs a pinned module (core patch 0031) |
| `param` | `size1:int:512:0:16384` and `size2:int:2048:0:16384`, the scratch units' sizes in KiB |
| `cpu`, `kabi`, `cc` | from the kit: `68030` / `k30.1.2` on k30, `68040` / `k46.1.2` on k46 |

It has no `rank`: it is not an sd disk controller.

The module's entry points:
- **`_load(params)`** runs in the root pass (C4-2 §2): process 0, level 7, the clock stopped.
  It sleeps on nothing, arms no timeout and requests no memory. It does three things:
  1. It reads `size1` and `size2` from the parameter string. Each takes C3-1's `int` form,
     decimal. If a value is absent, the module's default applies. If it is not a number, or
     lies outside 0–16384, the console says `ramdisk: sizeN is not a size of 0 to 16384 KiB;
     D taken` and the default applies.
  2. It calls `ramdisk_image()`. The DDI marks it "any" context: a plain getter.
  3. It works out unit 0's kernel address as above.

  It always returns 0, with an image or without one.
- **`_unload`** is never called by `moduload`, because `unload` is `never`. The core still calls
  it if a load fails after `_load` succeeded. It gives `EBUSY` while a unit is open. Otherwise
  it frees the scratch memory, forgets the image and returns 0. The image's memory is not the
  module's, so it is never touched.
- **`_halt`**: there is none (the wrapper's entry is 0; C4-2 §5). Nothing here interrupts or
  writes memory on its own.

It calls no `root_defer`: it has no interrupt.

The module imports only DDI names: `bcopy`, `getminor`, `iodone`, `kmem_free`, `kmem_zalloc`,
`printf`, `ramdisk_image`, `vtop`, and `mod_drvops` for the wrapper. `ramdisk_conf_data` is a
weak reference. Its globals are `ramdisk_drvdata` and `ramdisk_wrapper` only.

`iodone` is the block-completion call the stock `ram` driver makes. Like `ramdisk_image`, it
is a DDI name of kabi minor 2, so the module needs a kernel of k30.1.2 / k46.1.2 or later.

## Size and memory

amix-dlm's C3-1 §6 (version 4) limits a module's allocated image to 256 KiB and its file to
under 256 KiB. C4-4 §4 asks a root-class module to run in place: no section aligned above 16.
The figures are from the built objects. They are the same on both lines.

| | ramdisk | Limit |
|---|---|---|
| file (`mod.d/ramdisk`) | 4,630 bytes | under 256 KiB |
| allocated image (the size `modcheck` prints) | 2,944 bytes: `.text` 1,544, `.data` 372, `.moddata` 206, `.bss` 816 (aligned 8); no COMMON symbols | at most 256 KiB |

Its memory, beyond the image:
- **At load:** none. All state is static: three unit records in `.bss`, each with room for 64
  piece pointers.
- **At a scratch unit's first open:** the unit's size, in requests of at most 256 KiB, all
  `KM_NOSLEEP`. With the defaults, unit 1 takes 512 KiB (2 requests) and unit 2 takes 2 MiB
  (8 requests). The largest unit, 16 MiB, takes 64 requests.
- **Unit 0:** none. It is the loader's memory.

## Building

You need:
- the pinned gcc-cross-amix (`m68k-cbm-sysv4-*`, GCC 2.7.2.3) on `PATH`;
- `python3`;
- amix-dlm's built kits (`make kit` there), of kabi k30.1.2 / k46.1.2 or later, which carry
  `iodone` and `ramdisk_image`.

```sh
make -C ramdisk/module             # both lines
make -C ramdisk/module k46         # one line
make -C ramdisk/module test        # the host test (any host cc)
```

`DLM` names the amix-dlm checkout (default `../amix-dlm`). Alternatively, `KIT_k30` and `KIT_k46`
name the kits directly.

The objects are `ramdisk/build/k30/mod.d/ramdisk` and `ramdisk/build/k46/mod.d/ramdisk`. The
kit's `modfix` and `modcheck.py` check each one; `modcheck` prints `ok (k30.1.2, root, 2944
bytes)` and `ok (k46.1.2, root, 2944 bytes)`.

An older kit stops the build: one without `iodone` or `ramdisk_image` in its `ddi.list` at
`modfix: undefined: …`, and one whose `modcheck.py` predates block-only drivers (amix-dlm
186bd1f) at `drv_cmajor 0 (count 0): c:0 is not in majors=`.

## Packages (amix-dlm C3-5)

One package per line, minted by amix-packages:

| | k30 | k46 |
|---|---|---|
| catalog name | `ramdisk-k30` | `ramdisk-k46` |
| pkginst | `ramdisk30` | `ramdisk46` |
| version | `module/VERSION` | `module/VERSION` |

The short name `ramdisk` (7 bytes) still has to be added to C3-5 §1.1's table.

Each package has `CATEGORY` `system` and no scripts. It ships:
- `/etc/conf/mod.d/ramdisk`, the object;
- `/etc/conf/modreg.d/ramdisk`, comments only, because the package sets no parameter;
- the three nodes as pkgmap block-device entries: `/dev/dsk/ram0`, `/dev/dsk/ram1` and
  `/dev/dsk/ram2` (`b 20 0`, `b 20 1`, `b 20 2`).

**The node names.** The stock `core` package makes no node on block major 20: the stock `ram`
driver's nodes, if any, came from somewhere else. So the names follow the stock disks' own
convention instead: block nodes in `/dev/dsk`, with mode 0600 and owner root root, as
`/dev/dsk/c0d0s0` has them. There is no raw (`/dev/rdsk`) node, because the driver has no
character row.

## Testing

**`test/hosttest.sh`** runs on the host, with no box. It compiles the shipped `src/ramdisk.c`.
The one substitution is the K&R `printf` declaration, which it drops. Stub headers stand in
for the kernel's. The test provides the DDI names the module calls: it records every kmem
request, its size and its flag; `vtop` is the identity; and `bcopy` fails any copy that
crosses a buffer page or leaves a kmem piece or the image. It runs once with the k30 page
size (2 KiB) and once with the k46 one (4 KiB). It checks:
- the switch row (block major 20, no character row) and the absent `_halt`;
- the no-image path: `_load` returns 0, says nothing and requests nothing; unit 0 gives
  `ENXIO` and size -1;
- the scratch units:
  - allocated at the first open in `KM_NOSLEEP` requests of at most 256 KiB (2 MiB = 8
    requests, 16 MiB = 64, 300 KiB = 256 + 44);
  - zero-filled;
  - transfers across pieces and buffer pages, from an unaligned buffer;
  - the end-of-unit rules;
  - the open types;
  - freed at the last close;
  - `ENOMEM` with nothing left over when a request fails part way;
- the parameters: defaults, values, 0 (no unit), and values that are out of range or not a
  number;
- unit 0:
  - its size reported;
  - read and written in place;
  - never allocated or freed;
  - its data kept across close, and across `_unload`;
- an image across `VSECT1` (no unit 0, said) and one smaller than a block;
- `_unload`: `EBUSY` while a unit is open, otherwise the scratch memory freed.

**What cannot be tested here.** Unit 0 end to end needs boot2 to place an image and the kernel
to root on it. That is amix-dlm's S4-11 (boot2's placement), and the bench row S4-50. Until
then:
- the root mount from unit 0 has not run anywhere;
- neither has a scratch disk on a box: `mkfs`, mount and `/tmp` on unit 1 or 2.

The host test covers the driver's own logic. The kernel's side (`iodone`, `vtop` on a real
buffer, the block-row linkage) waits for the bench.
