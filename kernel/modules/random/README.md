# random — /dev/random and /dev/urandom

`random` gives Amix the two devices programs read random numbers from:

| Node | Device |
|---|---|
| `/dev/random` | `c 48 0` |
| `/dev/urandom` | `c 48 1` |

Both are the same generator. Neither ever blocks, and there is no entropy count, as on Linux's
`/dev/urandom` after its first seeding. Python's `os.urandom` and `secrets`, and with them its
`ssl` and its hash seeds, read `/dev/urandom` and treat it as a cryptographic source, so the
generator is a standard one.

It is a loadable kernel module of class `demand` for both Amix kernel lines, `k30` (68030) and
`k46` (68040/68060), built with the ABI kit from kernel/dlm. It has no static form.

## The generator

- **ChaCha20** (RFC 8439 §2.3) with a 256-bit key and a block counter. A read is the blocks
  of the key from counter 0, cut to the size asked.
- **Fast key erasure.** Every read ends by replacing the key with the first half of one more
  block, under a nonce no output block uses, which is never output. A later state therefore
  says nothing about bytes read before. Within one long read the key also changes every
  64 KiB.
- **Mixing in.** Input goes into the key 32 bytes at a time: XORed in, then the key becomes
  the first half of a block of the result under its own nonce, with the input's length in
  the nonce. Mixing in can only add to the key's uncertainty, never remove it, so anyone may
  write.
- **The inputs:**
  - what any process writes to either device: the boot step writes the saved seed, the date
    and the process table;
  - a sample at load, at every open and at every read: `lbolt`; the beam position (VHPOSR,
    `0xdff006`) three times, between the slow CIA accesses; the four timer bytes of CIA-A
    (`0xbfe401`–`0xbfe701`) and of CIA-B (`0xbfd400`–`0xbfd700`); a call count; and the size
    of the request or the minor.
- The chipset and the CIAs lie below `VSECT1`, where both lines map physical memory one to
  one (`phystokv`; cache-inhibited on k46, grimoire ✅). They are only read, and only
  registers whose reading changes nothing: never a TOD high byte, which latches the counter,
  nor an ICR, which reading clears. Kickstart leaves a CIA-A timer running (grimoire quirk
  §83), and this only reads it.
- **Sleeping readers.** `uiomove` may sleep on a page fault, and another reader may run in
  the meantime. The counter is therefore advanced before each copy, and no state is kept in
  locals across one, so no two outputs share a key and a counter.
- After a boot the sample alone is guessable. That is what the seed file is for.

## The boot step

`rc/randseed` is `/etc/init.d/randseed`, run as `/etc/rc2.d/S21randseed` and
`/etc/rc0.d/K02randseed`:

- **start** writes `/etc/random-seed` into `/dev/urandom`, followed by `date` and `ps -ef`.
  The first write loads the module. It then saves a fresh seed at once, so that a crash
  never reuses one.
- **stop** saves a fresh seed.
- The seed is 512 bytes, mode 0600, and replaces the old one only when it was read whole.
- S21 sorts after `S20devnodes`, which makes the package's nodes again if they are missing.
- Without the module or its node, the step writes one line on the console and in the boot
  log, keeps the old seed, and lets the boot go on.
- The log is `/var/adm/rc.log`, through amix-base's `rc.subr`; without it, the console.

## The module

| `.moddata` key | Value |
|---|---|
| `name` | `random` |
| `class` | `demand`: it loads at the first open of `/dev/random` or `/dev/urandom` |
| `majors` | `c:48` (registered to `random` in the kit's `registry/majors`, dlm a8719fb) |
| `unload` | `never`: the key holds what the boot step wrote, which a reload would lose |
| `cpu`, `kabi`, `cc` | from the kit: `68030` / `k30.1.2` on k30, `68040` / `k46.1.2` on k46 |

The entry points:
- `_load` takes the first sample.
- `open` accepts minors 0 and 1 and gives `ENXIO` for any other; `close` does nothing.
- `read` and `write` work as above.
- There is no `ioctl` and no `mmap`.
- `_unload` is called only when a load fails after `_load`; it clears the key.
- There is no `_halt`.

The module imports only DDI v1 minor-0 names: `getminor`, `lbolt`, `uiomove` and `mod_drvops`
for the wrapper; `random_conf_data` is a weak reference.

## Size and memory

| | random | Limit |
|---|---|---|
| file (`mod.d/random`) | 4,169 bytes | under 256 KiB |
| allocated image (`modcheck`) | 2,040 bytes: `.text` 1,652, `.data` 192, `.bss` 40; the rest is `.moddata` | at most 256 KiB |

It makes no kernel memory requests. A read uses 256 bytes of buffer and 64 bytes of block on
the stack, a write uses 32. The state is 40 bytes of `.bss`: the key, the counter and the call
count.

Speed has not been measured on a box yet; the bench row will record it. ChaCha20's 16-word
state does not fit the 68k's registers, and on k46 a spill goes to cache-inhibited memory.
Programs read 16 to 64 bytes at a time.

## Building

You need:
- the pinned gcc-cross-amix (`m68k-cbm-sysv4-*`, GCC 2.7.2.3) on `PATH`;
- `python3`;
- the built kits of kernel/dlm (`make kit` there) whose registry gives `c 48` to `random`.

```sh
make -C random/module              # both lines
make -C random/module k46          # one line
make -C random/module test         # the host tests (any host cc)
```

`DLM` names the dlm directory (default `../dlm`, that is `kernel/dlm`). Alternatively,
`KIT_k30` and `KIT_k46` name the kits directly.

The objects are `random/build/k30/mod.d/random` and `random/build/k46/mod.d/random`. The kit's
`modfix` and `modcheck.py` check each one. Two builds are byte-identical.

A kernel enforces the registry it was cut with. Kernels cut before `c 48 random` refuse the
module (`ECONFIG`).

## Packages (amix-dlm C3-5)

One package per line, rolled by `pkg/build.sh` (make dist's kspace step) through build/pkg's
`kmodpkg`, with `KM_ROOT` the checkout:

| | k30 | k46 |
|---|---|---|
| catalog name | `random-k30` | `random-k46` |
| pkginst | `random30` | `random46` |
| version | `module/VERSION` | `module/VERSION` |

Each package ships:
- `/etc/conf/mod.d/random`, the object;
- `/etc/conf/modreg.d/random`, comments only, because the module takes no parameter;
- `/dev/random` (`c 48 0`) and `/dev/urandom` (`c 48 1`), mode 0666, as package device
  objects of class `random`;
- `/etc/init.d/randseed` (`rc/randseed`, 0744 root sys), and the same bytes as
  `/etc/rc2.d/S21randseed` and `/etc/rc0.d/K02randseed`: copies, not links, because a
  kernel-space package is pure files (amix-dlm spec 40 §6);
- the pages, as the packages lay them out (userland/packages/docs/man-pages.md):
  `/opt/amix/man/7/random`, `/opt/amix/man/1m/randseed`, and the whatis fragment
  `/opt/amix/man/whatis.d/random30` or `random46`, the package instance. That one name is why
  each line has its own prototype.

`pin.sh` pins the objects, the licence and every shipped file by sha256, and names the kit's
amix commit (`KM_KIT_COMMIT`). A change to the boot step or a page is a new package version.
The catalog names come from `kernel/conf/names.conf` (`random30: random-k30`,
`random46: random-k46`).

## Testing

**`test/hosttest.sh`** runs on the host, with no box. It first checks the source: only the
CIA timer bytes and VHPOSR are read, and the major, the name and `unload` agree between
`random.c` and `module/keys`. It then compiles the shipped `src/random.c` by the host cc, with
the three hardware addresses pointed at test memory and stub headers for the kernel's, and
checks:
- the block function against RFC 8439 §2.3.2's test vector;
- four blocks against Python `cryptography`'s ChaCha20, when the host has it;
- the `cdevsw` row and the minors;
- that every read is the stream of the key the sample leaves, and that the key is replaced
  after it by the private block, and every 64 KiB within;
- that two reads never repeat, even with the hardware and the clock frozen;
- that each sampled input reaches the output, and a register it must not read does not;
- that writes mix in, their length counting, and an empty write changing nothing;
- a failed copy;
- a second reader while the first sleeps in `uiomove`: the counter advanced before each copy,
  and no block shared;
- `_unload`;
- 1 MiB of output: a chi-square of the byte counts, the share of bits set, and no repeated
  16-byte block.

**`test/rctest.sh`** runs the boot step under `sh`, with stand-ins for `dd`, `date`, `ps` and
`rc.subr`. It checks:
- the order of writes;
- the new seed's size and mode;
- the first boot;
- shutdown;
- no module;
- an unreadable device;
- the console without `rc.subr`;
- usage.

On the box: `dd if=/dev/urandom bs=16 count=1 | od -x` differs each time, and
`timex dd if=/dev/urandom of=/dev/null bs=4096 count=256` gives the speed.
