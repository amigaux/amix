# U4 — large kmem requests in a module's process context (2026-10-26)

- **Measurement:** U4 (90 §3, 30 §8): kmem requests of 64 KiB to 2 MiB,
  `KM_NOSLEEP` and then `KM_SLEEP`, from a module's `_load` in process
  context after multi-user (`modadmin -l` under development load).
- **Class:** bench (amiberry), plan item S3-41.
- **Tool:** the probe module `u4big` (`tests/bench/s3-41`), built with the
  kit; on the kernels of record, in a generation with the arena,
  `modadmin -K` first.
- **Evidence:** the Bench's runs N79 (k46, 128 MB in the CPU board's bank)
  and N80 (k30, 64 MB).

## 1. Results

| Request | k46 N79 (128 MB) | k30 N80 (64 MB) |
|---|---|---|
| `KM_NOSLEEP` 64 KiB | memory, 0 ticks | memory |
| `KM_NOSLEEP` 256 KiB | memory, 1 tick | memory |
| `KM_NOSLEEP` 512 KiB | failed | memory, 1 tick |
| `KM_NOSLEEP` 1 MiB, 2 MiB | failed | failed |
| `KM_SLEEP` 64 KiB, 256 KiB | memory, 0 ticks | memory |
| `KM_SLEEP` 512 KiB | **never returns** | memory |
| `KM_SLEEP` 1 MiB | (not reached) | **never returns** |

A `KM_SLEEP` request above what `KM_NOSLEEP` gives sleeps forever.
`modadmin -l` never returns, and the box does not shut down cleanly.

So in process context after multi-user, the largest single request:
- k46 at 128 MB: 256 KiB (it fails at 512 KiB);
- k30 at 64 MB: 512 KiB (it fails at 1 MiB).

Both are well below U1's figures at boot time (2 MiB and 1 MiB). The fixed
4 MiB kernel map that kmem's large requests share with `page[]` and the
u-areas (`grimoire-amix` ram-ceiling) is mostly spent once the box runs.
`page[]` is larger the more RAM there is, which is why k46 at 128 MB is
lower than k30 at 64 MB.

## 2. What it decides

- **For modules (30 §8, C3-6 §1):** a module's kmem requests are at most
  256 KiB each, on both lines. `KM_SLEEP` is only for requests of 256 KiB
  or less; a larger need is split, and every `KM_NOSLEEP` request is
  checked for failure. A module never makes one `KM_SLEEP` request above
  256 KiB: past the map's room it sleeps for ever.
- **For the core:** the core's own allocations for a module scale with it:
  the file buffer for the SHA-256 check, the symbol and string tables, and
  the image. All are `KM_SLEEP` (`dlm_zalloc`), and the image limit is
  2 MiB (C3-1 §4). So a module larger than about 256 KiB could hang
  `modload` the way U4 did. No module of stage 3 to 5 comes near that:
  the largest planned is cdfs at about 69 KB. Done (agreed 2026-10-26):
  C3-1 version 4 limits the image to 256 KiB and the file to under
  256 KiB (§6). The kit's `modcheck` refuses a larger module at build
  time, and core patch 0027 sets `dlm_maximage` to 256 KiB from the next
  kernel cut.
- **U2** was measured while u4big held its memory, so its figures (k46
  256 KiB, k30 512 KiB) are low. It is rerun clean with 64 KiB chunks.
